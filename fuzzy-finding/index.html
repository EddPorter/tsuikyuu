Best match first

Type a few letters into a fuzzy finder and it lists everything that contains them in order. That is often dozens of items, and the one you want has to be near the top. This page shows how a finder decides which match is best, from choosing the letters to scoring them to finding the best choice quickly, and how it stays fast on a list of thousands.

Matching is the easy part

The rule for a match is simple: the letters you typed must appear in the item, in the same order, with anything allowed in between. We met this as Letters in order on Just enough letters. But a short query matches a lot. Here is a made-up list of project files. Everything below uses it, and you can change it or load another.

Order

Which letters?

Ranking needs a score for each match. But even one item can match in several different ways, because each typed letter may be found in more than one place. Take rep and readme_report.md. A quick way to match is to take the first r, then the first e after it, then the first p after that. It works, but it scatters the letters. The letters of report sit together, at the start of a word, and are obviously what you meant.

Every way of placing the letters is listed, with its score from the rules in the next section. The first-found placement is tagged and so is the best one.

What makes a match good?

A finder scores a placement by adding up rewards and penalties for each matched letter. Typical rules, which this page uses in a simplified form:

Each matched letter
A small base reward, so longer queries that match score higher than shorter ones.
Start of the item
A bonus when a letter matches the very first character.
Start of a word
A bonus when a letter follows a separator such as /, ., _, - or a space, or begins a camelCase hump. People tend to type the starts of words.
Consecutive letters
A bonus when a letter immediately follows the previous matched letter, because a run of letters is much more likely to be what you meant.
Gaps
A penalty for letters skipped between two matches, charged more for starting a gap than for each extra letter in it.
Matching case
A tiny bonus when the typed letter has the same case as the item’s letter.

These numbers are made up for this page, in the spirit of how real finders work and not copied from any of them. Try the playground. Change a weight and watch the order change. Click a result to see its scorecard.

Finding the best placement

There can be a great many placements: a query of three letters in a long path might fit in dozens of ways, and the number grows quickly as the query and the item get longer. Trying them all is wasteful. Dynamic programming avoids it by remembering partial answers.

Build a grid with one row for each typed letter and one column for each letter of the item. Each cell holds the best score for matching the typed letters up to that row, with that row’s letter placed at that column. Cells where the letters differ stay empty. To fill a cell, look at the cells in the row above, to its left, and take the best of (their score plus this letter’s reward or penalty after that earlier match). The best score overall is the largest value in the last row, and following the choices back gives the placement.

The grid below is for the item and letters you chose above. The path in blue is the best placement. Pale cells are the ones the path could have used.

Each cell reuses answers already worked out for the row above. That is the whole idea of dynamic programming: solve small versions first, remember them, and build up. Staying fast on thousands of items

Scoring with a grid is cheap for one item, but a finder may hold tens of thousands of files and must answer after every keystroke. Two ideas keep it quick.

  • A cheap check first. Most items do not match at all. A single pass that takes the first letter found for each typed letter, the quick method from above, decides whether an item matches. Only the items that pass are scored with the grid.
  • Only re-check survivors. If you had typed re and now type rep, any item that fails re must fail rep. So each extra letter only needs to look at the items that matched before it.

The page breaks ties by the shorter item and then by list order. Real finders offer extra syntax for exact matches, prefixes and exclusions. In fzf, for example, 'term asks for an exact match, ^term for a prefix, term$ for a suffix and !term excludes items containing it.

Where to go next

Names to search for. They are pointers, not explanations.

Smith–Waterman
The dynamic-programming method for aligning two sequences in biology, scoring matches and gaps. A comment in fzf’s source describes its main matching function as a modified version of it, one that does not allow pattern letters to be skipped.
Edit distance
The number of insertions, deletions and substitutions needed to turn one string into another, found with a grid very like this one, built step by step on What changed?. It forgives typos, where letters-in-order forgives gaps.
Trigram index
Splitting text into three-letter pieces and indexing them, so a search can skip most of a large list. Russ Cox’s article “Regular Expression Matching with a Trigram Index” describes how Google Code Search worked this way.
Levenshtein automaton
A machine that recognises all words within a given edit distance of a query, used to search dictionaries quickly.

In short

  • A fuzzy match is letters in order. A short query matches a lot, so ranking decides whether the finder is any use.
  • One item can match in many ways, and the first letters found are often not the ones you meant.
  • A score adds rewards for letters that start words and sit together, and penalties for gaps.
  • Dynamic programming finds the best-scoring placement by remembering the best answers for shorter queries.
  • A cheap check first, and re-checking only survivors, keep it fast on long lists.
