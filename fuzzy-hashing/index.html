Nearly the same

A mass mailer sends one message to millions of people, with small changes in each copy. An ordinary fingerprint cannot connect them. This page builds up the idea of a fuzzy fingerprint, where similar messages give similar fingerprints, and uses it to find a whole campaign without comparing every message with every other.

Why an ordinary hash is not enough

A hash turns any text into a short fingerprint. Identical messages give identical fingerprints, so a mail system that has seen a message once could recognise every other copy at a glance. The trouble is that a hash is built to change completely when its input changes even a little. Add one reference code to a copy and the fingerprint has nothing in common with the original.

A mass mailer can exploit this deliberately. If every copy gets its own random tweak, no two copies share a fingerprint. What we want is the opposite property: a fingerprint that stays similar when the message stays similar.

Pieces again: shingles

The first step is one you have seen on the other pages: cut the thing into overlapping pieces. For text, the usual pieces are runs of a few consecutive words, called shingles. First tidy the message by making it lower case and removing punctuation, so that trivial differences do not count. Then slide a window of k words along it.

Two messages that are mostly the same share most of their shingles. A single changed word only spoils the k shingles that contain it. This is the same idea as the pieces of a word in Just enough letters, applied to words instead of letters.

Similarity is the shared shingles divided by all the different shingles in either message. It is called the Jaccard similarity: 100% for the same shingles, 0% for none in common.

Comparing every pair does not scale

We could now compare every message with every other, using shingle sets. But the number of pairs grows with the square of the number of messages.

A real system would have billions of messages to consider. What it needs is a short summary of each message such that similar summaries are easy to find without looking at every pair.

MinHash: a short summary that keeps the similarity

Here is the trick. Pick a random hash function and apply it to every shingle in a message. Keep only the smallest value. Do the same for another message with the same function. The surprising fact is that the two smallest values are equal exactly when the single shingle that hashed lowest across both messages is in both. The chance of that is the Jaccard similarity itself.

One such value is a very noisy guess. Repeat it with many different hash functions and keep all the minimums. That list is the message's signature, and the fraction of positions where two signatures agree estimates the similarity. Slide the signature length and see how the estimate settles.

Finding likely twins without comparing every pair

Signatures are short, but comparing every pair of them is still every pair. The next trick is to avoid most comparisons altogether. Cut each signature into b bands of r positions. Give each band a label made of its values. Two messages are candidates if they share a whole band label, which is a lookup in a table of labels. This is an index, just like the one on Just enough letters: instead of asking every message about every other, you look up who else has the same band.

More rows per band makes a match harder to get by chance, so it favours very similar pairs. More bands gives more chances, so it catches less similar ones. The curve shows the chance that a pair of a given similarity becomes a candidate.

Try the settings. Raise the confirmation level, or use fewer, longer bands, and the mailings start to fall out of their groups. Lower it, and the genuine delivery note joins the parcel group. Look at the invoice group: the genuine invoice stays in it until the setting is strict enough that real mailings start dropping out too. That message is as similar to the mailings as they are to each other, so no setting separates them cleanly. Similarity can show that messages are alike, but not that they are unwanted.

Another way: SimHash

MinHash is not the only fuzzy fingerprint. SimHash turns a message into one short string of bits. Each shingle hashes to a pattern of bits. For every bit position, count how many shingles have a 1 there against a 0, and let the majority decide that bit of the fingerprint. Similar messages vote the same way on most bits, so the number of bits that differ (the Hamming distance) is small. Here are the fingerprints of your two messages from above.

Other fuzzy fingerprints

ssdeep
Context-triggered piecewise hashing. A rolling hash decides where to cut a file into chunks, hashes each chunk, and the digest is a string of small pieces, so inserting or deleting text only changes the chunks nearby. It compares files, such as sets of related malware, and not only text.
TLSH and Nilsimsa
Digests built from counts of small patterns of bytes, designed so that the distance between two digests reflects how similar the inputs are. Nilsimsa was designed with spam detection in mind. I am recalling both from memory, so check them before relying on this.
Pyzor, Razor and DCC
Open anti-spam systems that share fingerprints of messages between many mail servers, so that one server's sighting helps all the others. I recall that they publish how they work, but check each before relying on that.

What this cannot do

  • A fingerprint is a signal, not a verdict. A group of near-identical messages might be a spam campaign, or a company's legitimate newsletter, or a receipt sent to thousands of customers. Real systems combine similarity with other evidence, such as how many recipients, how people react and where the mail came from.
  • Senders adapt. Anything that reads the words can be tricked by changing the words enough, or by putting the message in an image. This page is about the idea, not about beating or defeating any particular filter.
  • It reads the message. Text fingerprinting looks at the content of mail. Whether that is acceptable is a question about privacy as well as engineering, and different services answer it differently.
  • Nobody outside publishes the details. Large mail providers do not describe how their filters work, so this page cannot say what any of them does. It describes the public techniques.

Locality-sensitive hashing
The family of ideas this page used: hash so that similar things land together. Banding is one scheme of it.
Shingling and min-wise hashing
I believe these were introduced for finding near-duplicate web pages in the late 1990s, by Andrei Broder and colleagues. Check before citing it.
Charikar's SimHash
The bit-vote fingerprint above, with schemes for searching by small Hamming distance.
Weighted MinHash and b-bit MinHash
Variants that count repeated shingles, or store fewer bits per position.
Edit distance
A different idea of “nearly the same” that counts the changes needed to turn one text into another. It is more precise and much slower.

In short

  • An ordinary hash changes completely when its input changes a little, so near-copies of a message look unrelated.
  • Cutting a message into shingles lets you measure how much two messages overlap.
  • MinHash squeezes each message into a short signature whose agreement estimates that overlap.
  • Splitting signatures into bands finds likely twins by lookup, without comparing every pair.
  • The settings trade missed campaigns against wrong groupings, and the result is a signal rather than a verdict.
