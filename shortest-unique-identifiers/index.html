Just enough letters

To pick one word out of a list you rarely need the whole word. This page works out the fewest letters that do the job, one step at a time. Then it shows why the obvious method gets slow, how an index fixes that, and what changes when you change the rules.

What we are after

Picture a list of words and a search box. Type a few letters and every word that contains them lights up. Some pieces light up many words. Some light up just one, and a piece that lights up only one word is enough to pick that word out. For each word in the list we want the shortest piece like that.

Can you make exactly one word light up with a single letter? With two? The rest of the page is about getting a computer to do this for every word, and to do it quickly.

Pieces of a word

To find the shortest piece by method instead of by hunch, first list every piece of a word: every run of letters that sit side by side. A word with n letters has n × (n + 1) ÷ 2 pieces, although some repeat. The grid shows them shortest first, left to right within each length. The small number on each piece is how many words in your list contain it.

Why shortest first? Because then the first piece that works is also the shortest one that works, and we can stop looking. If two pieces tie for length, we take the leftmost.

The plain method

Now the method as a loop. For each word, take its pieces in order. For each piece, ask every word whether it contains the piece, and count the yes answers. If only one word says yes, that piece is the answer, so keep it and move on to the next word. Step through it below. Why that gets slow

Every piece costs one question per word. Then the same questions come round again for the next word. The checks counter in the walk-through above is counting them.

Most of that work is repeated. The question “which words contain na?” gets asked again every time a piece na turns up, and the answer never changes. The cure is to ask each question once and write the answer down.

Writing the answers down: an index

Think of the index at the back of a book. Instead of reading every page to find where “tea” appears, you look up “tea” and get the page numbers. We can build the same thing for pieces: a table with one row per piece, listing the words that contain it.

Build it by going through the words one at a time. For each piece of the word, add the word to that piece's row. A word is added once per piece, even if the piece appears twice in it. Add the words below and watch the table grow.

    Scan or index?

    Neither is always better. The index pays up front, by writing a row for every piece of every word, and after that each piece costs one lookup. Scanning pays nothing up front but asks every word about every piece. The index also costs memory, which scanning does not, and that comes after the chart. With a few words the up-front cost is not worth paying. As the list grows the checks multiply and the index pulls ahead. Both always give identical answers.

    The cost the chart does not show: memory

    The chart counts work. It does not show memory, and there the two methods differ sharply. Scanning needs no extra memory at all. The index holds a row for every piece of every word, and each row repeats the letters of its piece. A word of n letters has up to n × (n + 1) ÷ 2 pieces, so its rows hold roughly n³ ÷ 6 letters in total. Double the length of the words and the table grows about eightfold. That is the other half of the trade-off.

    A trie (there is a whole page on them, Shared beginnings) can hold the same index in less space, because it shares letters. The pieces na, nan and nana all start the same way, so a trie stores that path once instead of three times, one letter per node instead of a whole string per row. For one word that brings the growth down from about n³ to about n² letters. If the runs of nodes with a single path are squashed into one edge each, the trie becomes a suffix tree, which needs at most about 2n nodes for a word of n letters, so it grows in step with the word's length.

    Real memory also depends on the links between nodes, and every node needs room for them, so fewer letters is not the same as fewer bytes. Treat these numbers as a guide to how the structures grow, not as exact sizes. All three also need the list of words for each piece. With short words the three are close in size. The gap opens up as words get longer: try typing a single word of ten different letters, such as abcdefghij.

    Changing the rules

    The loop has three parts that can be swapped without touching the rest, and each answers a different question.

    PartOptionsWhat changes
    matchContains, starts with, letters in orderWhat counts as a match: *id*, a git-style prefix, or the letters of a fuzzy finder.
    goalOnly this word, at most two, every wordUnique identifiers, a short list of candidates, or the longest text the words all share.
    counterScan, indexNothing about the answers. Only the amount of work.

    Things to try

    • Pick Starts with. Identifiers now have to be prefixes, like short git hashes, and they get longer.
    • Pick Letters in order. Gaps are allowed, the way a fuzzy finder matches. Some answers get shorter (try DNA), most stay the same, and a word can lose its answer completely: with the Bananas preset, banana has none, because every ordered selection of its letters is also in bandana.
    • Load Nested. Some words contain no piece that another word lacks, so they get no identifier at all.
    • Set the goal to Every word. The loop now looks for the longest text all the words share. Load DNA to see a tie: two pieces are equally long, and each word keeps the first one it meets, so the answers differ.

    Fuzzy finding: the same rules in your editor

    The Letters in order rule is how a fuzzy finder works. Type a few letters and every item that contains them in that order, with gaps allowed, is a match. The file pickers in code editors, and tools such as fzf, work this way. Try it on your words, and load Files or Trees for more to search.     A third way: sort the endings

    The loop above could answer many different questions, because you could swap its rules. The sorting method is a specialist. It answers exactly one of them, the one this page began with. In the playground's terms that is Contains with Only this word, a problem usually called the shortest unique substring problem. A substring is a run of letters side by side. That is different from a subsequence, which is letters in order with gaps allowed, the playground's third option.

    Playground choiceDoes sorting the endings answer it?
    Contains, only this wordYes. This is the problem it solves.
    Starts with, only this wordYes, in a simpler form. Sort the whole words instead of their endings and compare each word with its neighbours.
    Letters in orderNo. The trick depends on pieces being runs of letters, because the endings that match a run sit together once sorted. Letters with gaps in between do not.
    At most two wordsNot covered here.
    Every wordA different question: the longest text all the words share. Suffix structures can answer it quickly, but not by this neighbour comparison.

    The idea in five steps

    1. List every ending of every word. banana gives banana, anana, nana, ana, na and a.
    2. Sort the whole list alphabetically. Endings that start with the same letters end up next to each other.
    3. A piece is in another word only if some ending of that word starts with it. If so, that ending sits right beside ours in the sorted list. So we only need the nearest ending from a different word, above and below.
    4. Count how many letters our ending shares at the start with each of those two neighbours, and take the larger number.
    5. One more letter than that makes the piece start differently from every ending of every other word, so only this word has it. Do this for each of the word's endings and keep the shortest piece, the leftmost if there is a tie.

    Now walk through it. Pick a word, then step through its endings. Yellow letters are shared with a neighbour from a different word. The blue letter is the one extra letter that makes the piece unique.

      In short

      • A short identifier is the first piece, shortest first, that no other word contains.
      • Scanning asks every word about every piece. It is simple, but the work multiplies with the number of words.
      • An index asks each question once and writes the answer down. It costs more up front and a lot more memory, and then one lookup per piece. A trie or suffix tree can shrink that memory.
      • Swapping how a search matches, or what you want from the matches, changes the answers without changing the loop.
      • Sorting the endings reaches the same answers without trying pieces at all, but only for one question: the shortest unique substring.

      Where to go next

      This page used the simplest methods that show the ideas. These are the names to search for when the lists get bigger. They are pointers, not explanations.

      Trie
      A tree of letters (see Shared beginnings). For the starts with rule it gives the shortest unique prefix directly: walk down from the root and stop at the first node that only one word passes through. The index above holds the same information as a trie of every ending of every word, and a trie holds it in less space because it stores each shared run of letters once.
      Rolling hash and binary search
      If a word has a unique piece of some length, it has one at every longer length up to its own, because you can extend the piece. So the shortest length can be found by binary search. At each length, hash every piece of that length in one pass (a rolling hash, as in the Rabin–Karp algorithm) and count the words each hash appears in. Hashes can collide, so a careful version checks what it finds.
      Aho–Corasick
      Matches many patterns against a text in a single pass. Loading all the candidate pieces into one such automaton would let the scan method ask all of its questions about a word at once.
      Suffix array and LCP array
      The sorted-endings table is this idea. The sorted list is a suffix array, and the shared-letters column is the LCP array. Both can be built in time proportional to the total length of the words (SA-IS and Kasai's algorithm are the usual names), which is why real tools use them.
      Suffix tree and suffix automaton
      The same information held as a tree or an automaton, again in linear time (Ukkonen's algorithm builds a suffix tree). The generalised versions handle many words at once. They also find the longest text all the words share, which is the Every word goal, far faster than the brute force here. The research name for counting how many different words contain a piece is document counting.
      FM-index, k-mers and Bloom filters
      Compressed or approximate versions of these ideas for inputs as big as genomes: the Burrows–Wheeler transform and the FM-index, counting fixed-length pieces called k-mers, and Bloom filters for approximate membership. Finding stretches of DNA that occur only once matters when designing primers, so the DNA preset is closer to real use than it looks.
